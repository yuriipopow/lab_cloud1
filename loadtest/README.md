# Навантажувальний тест (k6)

Профіль «мало записів, багато читань»: кожен віртуальний користувач у циклі робить 1 запис (`POST /api/notes`) і 9 читань (4 рази список, 3 записи за id, включно зі щойно створеним, 2 рази дані автора). Фази: 3 хв наростання до N, 5 хв стале навантаження, 2 хв спад.

## Встановлення

```bash
brew install k6
```

## Запуск

Адреса береться з `terraform output`, N = 100 за замовчуванням (підібрано так, щоб спрацьовувало масштабування):

```bash
./loadtest/run.sh
```

З явною адресою, N і назвою звіту (так запускались прогони для `docs/`):

```bash
LABEL=no-cache ./loadtest/run.sh http://<alb-dns> 100
```

Параметри через змінні середовища: `RAMP_UP` (3m), `STEADY` (5m), `RAMP_DOWN` (2m), `THINK` (0.3 с між запитами).

Якщо API працює в режимі черги (`write_mode = queue`), `POST` повертає `202`. Сценарій тоді опитує статус запису (`GET /api/requests/{id}`) до `POLL_MAX` разів (за замовчуванням 3) і лише потім читає щойно створений запис. У звіті з'являються час від `202` до виконання і кількість записів, не готових після опитувань.

Після тесту дочекайтеся, поки кількість екземплярів повернеться до 1 (~15–20 хв):

```bash
aws ecs describe-services --cluster lab-cloud-cluster --services lab-cloud-service --query 'services[0].[desiredCount,runningCount]'
```

## Результати

Підсумковий звіт (кількість запитів, частка помилок, p50/p95/p99, частка влучань у кеш) виводиться в консоль і зберігається в `results/<LABEL>.json` і `.md`:

- `results/no-cache.*` — прогін без кешу, N = 100;
- `results/cache-on.*` — прогін з кешем Redis, N = 100;
- `results/queue.*` — прогін із записом через чергу SQS, N = 100 (`docs/QUEUE.md`).

Аналіз — у [`docs/LOADTEST.md`](../docs/LOADTEST.md) і [`docs/CACHE.md`](../docs/CACHE.md).
