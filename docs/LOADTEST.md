# Навантажувальне тестування

Інструмент: [k6](https://k6.io) (`brew install k6`). Сценарій: [`loadtest/script.js`](../loadtest/script.js), запуск: [`loadtest/run.sh`](../loadtest/run.sh).

## Запуск

```bash
./loadtest/run.sh
```

Без аргументів адреса береться з `terraform output alb_dns_name`, а N = 100 — значення, підібране так, щоб на сталому навантаженні спрацьовувало масштабування (див. «Підбір N»). Явні параметри:

```bash
LABEL=cache-on ./loadtest/run.sh http://<alb-dns> 100
```

Підсумковий звіт виводиться в консоль і зберігається в `loadtest/results/<LABEL>.json` та `.md`.

| Змінна | За замовчуванням | Призначення |
|---|---|---|
| `VUS` (2-й аргумент) | 100 | N — кількість віртуальних користувачів на сталому навантаженні |
| `RAMP_UP` | `3m` | наростання 0 → N |
| `STEADY` | `5m` | стале навантаження з N користувачами |
| `RAMP_DOWN` | `2m` | спад N → 0 |
| `THINK` | `0.3` | середня пауза між запитами користувача, с (випадково 0,5–1,5×) |
| `LABEL` | `run-<дата>` | назва файлу звіту |

Тривалість одного прогону — 10 хвилин.

## Профіль користувача

Один VU у циклі виконує **1 запис і 9 читань** (співвідношення записів до читань — 1:9):

1. `POST /api/notes` — створення запису (JWT отримується один раз у `setup()`).
2. `GET /api/notes` — список (×4).
3. `GET /api/notes/{id}` — щойно створений запис (×1) і випадкові записи зі списку (×2).
4. `GET /api/authors/{id}` — дані автора (×2).

Між запитами є пауза `THINK`, тож один VU генерує приблизно 2–3 запити за секунду.

## Підбір N

Мета — щоб на сталому навантаженні середнє CPU перевищило 60 % і спрацювало масштабування.

Спершу виконано короткий калібрувальний прогін: N = 60, 45 с наростання і 1,5 хв сталого навантаження. Це менше за 3 хв, потрібні масштабуванню, тож нових екземплярів не з'являлося. Результат: середнє CPU одного екземпляра ~56 %, ~136 запитів/с, p95 117 мс. Цього замало: ціль 60 % перетиналася б ледь-ледь, а поріг сповіщення 70 % — ні.

CPU зростає майже лінійно з кількістю користувачів (~0,93 % на VU), тому для ~85–90 % на одному екземплярі взято **N = 100**. На сталому навантаженні це дало 81–83 % CPU: впевнено вище за ціль масштабування і поріг сповіщення.

## Чому середнього значення латентності недостатньо

p50, p95 і p99 — це значення, швидше за які обслуговано відповідно 50 %, 95 % і 99 % запитів. Середнє «розмазує» хвіст: якщо 98 запитів тривали 10 мс, а 2 — по 2 с, середнє становить ~50 мс і виглядає добре, хоча кожен п'ятдесятий запит обслуговано дуже повільно. Користувач робить десятки запитів за сеанс, тож хвіст він відчуває майже напевно.

## Навіщо фаза наростання

- Автомасштабування потрібен час. Стрибок одразу до N — це сценарій «DDoS», а не реальне зростання трафіку.
- Пул з'єднань до БД, JIT V8 і кеш «прогріваються» поступово, тож результати холодного старту не змішуються зі сталим режимом.
- Під час наростання видно, за якого навантаження сервіс починає деградувати.

## RPS і кількість одночасних користувачів

За законом Літтла: **RPS ≈ VU / (латентність + пауза)**. Якщо латентність росте при тій самій кількості VU, RPS падає: кожен користувач чекає довше і рідше надсилає запити. Тому для фіксованого RPS потрібно «відкрите» навантаження (`constant-arrival-rate`), а `ramping-vus` моделює саме кількість користувачів.
