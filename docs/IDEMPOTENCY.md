# Ідемпотентність операцій запису (бонус 7)

Код: `idempotency` у [`app/src/index.js`](../app/src/index.js), `insertNote` у [`app/src/lib.js`](../app/src/lib.js), тест — [`app/test/idempotency.test.js`](../app/test/idempotency.test.js).

## Яку проблему це розв'язує

Клієнт надсилає `POST /api/notes`, а відповідь не доходить: обрив мобільного зв'язку, тайм-аут на балансувальнику, перезапуск екземпляра під час graceful shutdown. Клієнт не знає, чи запис створено, і повторює запит. Без захисту повтор створює **дубль**. Для нотатки це дрібниця, а для оплати чи замовлення — подвійне списання.

`GET`, `PUT` і `DELETE` ідемпотентні за визначенням HTTP: повтор не змінює результату. `POST` і `PATCH` — ні. Заголовок `Idempotency-Key` робить `POST` безпечним для повтору: клієнт генерує унікальний ключ (UUID) на **одну логічну операцію** і надсилає той самий ключ у кожній спробі.

## Як працює

```text
POST /api/notes   Idempotency-Key: 7f3c…   {"content":"…"}
        │
        ▼
SET idem:7f3c… {"state":"processing","fingerprint":sha256(body)} NX EX 60
        │
   ┌────┴─────────────── ключ уже був ───────────────┐
   │ OK: виконуємо запит                              │
   ▼                                                  ▼
запис у БД (sync, 201) або в SQS (queue, 202)    state = done → та сама відповідь,
   │                                              Idempotent-Replayed: true
   ▼                                              state = processing → 409 + Retry-After
SET idem:7f3c… {"state":"done", status, body}     інший fingerprint → 422
    EX 86400 (24 год)
```

- **Атомарне захоплення ключа** `SET … NX` гарантує, що з кількох одночасних запитів із тим самим ключем (зокрема на різних екземплярах API за ALB) виконається лише один. Redis спільний для всіх екземплярів.
- **Fingerprint тіла** (SHA-256): той самий ключ з іншим тілом — помилка клієнта, відповідь `422`, а не мовчки стара відповідь.
- **Стан «processing» живе 60 с**: якщо екземпляр впаде посеред запиту, ключ звільниться сам, і клієнт зможе повторити. Готова відповідь зберігається **24 години**.
- **Помилки 5xx не зберігаються**: ключ видаляється, і повтор виконається заново.
- **Без Redis** запит із ключем отримує `503`. Краще чесно відмовити, ніж виконати без гарантії.
- **Другий рівень захисту — у БД**: колонка `notes.idempotency_key UNIQUE` і `INSERT … ON CONFLICT (idempotency_key) DO UPDATE … RETURNING`. Навіть якщо запис у Redis зникне (витіснення, перезапуск), повторна вставка поверне наявний рядок, а не створить новий.

## Тест

```bash
cd app && BASE_URL=http://<alb-dns> npm test
```

Тест перевіряє «один запис у базі» через лічильник записів автора (`GET /api/authors/10`, не кешується): після двох однакових запитів він має зрости рівно на 1.

Результат проти хмари (2026-11-20, `WRITE_MODE=queue`):

```text
ok 1 - два однакові запити з одним Idempotency-Key: один запис у базі, дві однакові відповіді
ok 2 - той самий ключ з іншим тілом -> 422, нічого не створюється
ok 3 - одночасні запити з одним ключем: виконується лише один
ok 4 - контроль: без ключа два запити створюють два записи
# tests 4
# pass 4
# fail 0
```

Ті самі 4 тести проходять і локально (`docker compose up`) в обох режимах, `WRITE_MODE=sync` і `WRITE_MODE=queue`.

Приклад вручну:

```bash
KEY=$(uuidgen)
curl -si -X POST <base>/api/notes -H "Authorization: Bearer $T" -H "Idempotency-Key: $KEY" \
     -H 'Content-Type: application/json' -d '{"content":"x","author_id":10}'
# HTTP/1.1 202 Accepted   {"requestId":"…","status":"pending","statusUrl":"/api/requests/…"}
curl -si -X POST … те саме …
# HTTP/1.1 202 Accepted   Idempotent-Replayed: true   — той самий requestId, нове повідомлення в чергу не пішло
```

## Як поєднується із завданням 6 (черга)

Ідемпотентність потрібна на **обох кінцях** черги:

1. **Клієнт → API.** Повторний `POST` з тим самим `Idempotency-Key` повертає збережену відповідь `202` з тим самим `requestId`, і **друге повідомлення в чергу не потрапляє**.
2. **Черга → обробник.** SQS гарантує доставку «щонайменше один раз»: те саме повідомлення може прийти двічі (обробник упав після запису в БД, але до `DeleteMessage`, або не встиг за `VisibilityTimeout`). `requestId` з повідомлення стає `idempotency_key` рядка в БД, тож повторна обробка натрапляє на `ON CONFLICT` і **не створює дубль**. Обробник лише пише в журнал `{"type":"duplicate", …}` і видаляє повідомлення.

Перевірено локально: те саме повідомлення надіслано в чергу двічі, і результат — один рядок у `notes` та запис `duplicate` у журналі обробника (`docs/QUEUE.md`).

Без ідемпотентного обробника гарантія «щонайменше один раз» перетворилася б на «іноді двічі». Разом вони дають **ефективно рівно один раз** (effectively-once): повідомлення може доставлятися кілька разів, але ефект стається один раз.

## Обмеження

- Ключі живуть у Redis на Fargate без збереження на диск. При перезапуску Redis збережені відповіді зникають, і повтор після цього виконається заново. Дубль у БД при цьому не з'явиться завдяки `UNIQUE`, але в режимі `sync` клієнт отримає `201`, а не збережену відповідь. У продакшні — ElastiCache з реплікою або окрема таблиця ключів у БД.
- Політика `volatile-lru` при нестачі пам'яті витісняє ключі з TTL. За 128 МБ і ~300 байт на ключ це ~400 тис. ключів. Для реального потоку записів пам'ять або TTL треба рахувати.
