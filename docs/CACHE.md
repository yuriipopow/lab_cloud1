# Кешування операцій читання

## Що кешується

Найбільш навантажена операція — **`GET /api/notes`**: 4 з 9 читань у сценарії, до того ж запит з `JOIN authors` і `ORDER BY`. Вона працює за схемою **cache-aside** (`app/src/index.js`):

1. Сервіс читає ключ `notes:list:v1` з Redis.
2. Якщо ключ є (TTL не сплив) — повертає його вміст, заголовок `X-Cache: HIT`.
3. Інакше читає з PostgreSQL, записує в Redis з `EX = 30` с і повертає дані, заголовок `X-Cache: MISS`.
4. Якщо Redis недоступний, сервіс працює напряму з БД: кеш — це оптимізація, а не залежність.

## Інфраструктура кешу

Замість ElastiCache (~$12–16/міс) використано **окремий Fargate-сервіс `redis:7-alpine`** ([`terraform/redis.tf`](../terraform/redis.tf)):
- DNS-ім'я в VPC через AWS Cloud Map: `redis.lab-cloud.local`;
- Security Group пускає порт 6379 лише від SG сервісу API;
- без збереження на диск (`--save ""`), `maxmemory 128mb` + `allkeys-lru`.

Увімкнення та вимкнення: змінна Terraform `cache_enabled` → env `CACHE_ENABLED`:

```bash
terraform -chdir=terraform apply -var cache_enabled=false   # без кешу
terraform -chdir=terraform apply -var cache_enabled=true    # з кешем
```

### Чому не кеш у пам'яті процесу

За кількох екземплярів за ALB у кожного свій кеш:
- **частка влучань падає в N разів**: кожен екземпляр окремо «прогріває» свою копію, і кожен окремо ходить у БД після закінчення TTL;
- **користувачі бачать різні дані**: два послідовні запити потрапляють на різні екземпляри з різним віком кешу, і запис може то з'являтися, то зникати;
- **інвалідація неможлива**: екземпляр, який обробив запис, може видалити ключ лише у власній пам'яті;
- новий екземпляр після масштабування стартує з холодним кешем, а пам'ять дублюється N разів.

Спільний Redis дає одну копію даних для всіх екземплярів, один TTL і одну точку інвалідації.

**Частка влучань у кеш: 99,9 %.** За k6 (заголовок `X-Cache`) — 99,9 %; за журналом застосунку — 50 781 влучання і 63 промахи (99,88 %).

**Як читати результат.**
- Кешується лише список (`GET /api/notes`), а це 4 з 10 запитів сценарію. Тому кількість запитів до БД впала не в рази, а на ~39 %: майже рівно на частку списку (40 %). Інші читання (за id, автор) і запис і далі йдуть у БД.
- CPU RDS майже не змінився, бо база тут не була вузьким місцем (≤ 13 % в обох прогонах). Для `db.t4g.micro` важить не CPU, а те, що з кешем база має на ~40 % більше запасу для зростання навантаження.
- Вузьке місце — CPU контейнера API (0,25 vCPU, Node.js): HTTP, JSON і драйвер PostgreSQL. Кеш прибрав найважчий запит (JOIN + ORDER BY), і CPU API знизився на ~10 п. п., а латентність на ALB — приблизно на 40 %. У k6 різниця p95 менша, бо там ~30 мс займає мережа між клієнтом в Україні і `eu-north-1`.
- Найбільший виграш — у хвості: p99 упав на 21 %, бо зникли повільні запити списку під час черги до пулу з'єднань БД.

Запит у CloudWatch Logs Insights (лог-група `/ecs/lab-cloud`), який сумує лічильники з усіх екземплярів:

```
fields @timestamp, @message
| filter type = "stats"
| stats sum(cacheHits) as hits, sum(cacheMisses) as misses, sum(dbQueries) as db,
        100 * sum(cacheHits) / (sum(cacheHits) + sum(cacheMisses)) as hit_ratio_pct
  by cacheEnabled
```

Теоретична оцінка: за TTL 30 с маємо щонайменше 1 промах на 30 с, а одночасні промахи на межі TTL дають кілька. На сталому навантаженні список запитують ~85 разів на секунду (40 % від ~211 запитів/с), тобто ~2 500 разів за 30 с. Отже частка влучань ≈ 1 − 1/2500 ≈ 99,9 %. Це збігається з виміряним: 63 промахи за 10 хв — це ~20 вікон TTL по 1–3 промахи (малий stampede на межі TTL, коли кілька екземплярів одночасно бачать порожній ключ).

## Актуальність даних

**Скільки часу клієнт може бачити застарілі дані після запису.** У поточній конфігурації кеш списку після `POST` **не інвалідується**, тож новий запис може не з'являтися в `GET /api/notes` **до 30 с** (TTL). Окремий запис за id (`GET /api/notes/{id}`) не кешується, тому щойно створений запис доступний одразу.

**Як цей час зменшити:**
1. **Інвалідація при записі**: після `INSERT` видаляти ключ `notes:list:v1`. Це вже реалізовано за прапорцем `CACHE_INVALIDATE_ON_WRITE=true`. Наступне читання піде в БД. Залишається коротке «вікно гонки»: читач, що почав читання з БД до запису, може покласти в кеш старі дані вже після видалення. Його закриває версіонування ключа або повторне видалення із затримкою (delayed double delete).
2. **Write-through**: при записі одразу оновлювати кешований список.
3. **Менший TTL**: 5–10 с знижує застарілість, але частіше звертається до БД.
4. За профілю «багато записів» (тут кожна ітерація k6 щось пише) інвалідація на кожен запис фактично вимикає кеш. Тому тут свідомо обрано TTL без інвалідації: для стрічки постів затримка в 30 с прийнятна.

## Лавинне звернення до БД (cache stampede)

Коли ключ спливає під навантаженням, усі одночасні запити отримують промах і всі разом ідуть у БД. Способи уникнути:
- **блокування**: лише один запит перебудовує кеш (`SET key:lock NX EX 5`), інші чекають або віддають старе значення;
- **stale-while-revalidate / рання ймовірнісна перебудова**: оновлювати ключ трохи раніше за TTL у фоні;
- **джитер TTL** (30 ± 5 с), щоб ключі не спливали одночасно;
- request coalescing у межах процесу (один `Promise` на ключ).
